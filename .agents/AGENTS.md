# 전사 시스템 개발 표준 헌장 (System Development Standards)

---

## 🏛️ [카테고리 I] 시스템 최우선 사명 및 핵심 가치 (System Core Mission & Principles)

### 1.1 최우선 개발 사명 (System Core Mission)
> **"최대 편리함과 담당자의 노력 대비 효과와 이익(효익)을 합쳐서, 최대 편익에 이르는 시스템 개발이 우리의 목적이다."**
- 모든 개발, UI/UX 설계, 비즈니스 도메인 연동 시 단순 코드 완성이 아닌 **임직원의 최소 노력으로 최대 업무 효익과 이익(최대 편익)을 창출하는 것**을 절대적인 최우선 사명으로 준수한다.

### 1.2 렌탈 도메인 3대 핵심 가치 (3 Core System Values)
개발 및 기능 수정 시 단순 UI 변경에 그치지 않고, 아래 3대 핵심 가치를 최우선적으로 반영한다:
1. **렌탈 자산의 효과적인 운용**: 자산 상태(임대가능, 출고대기, 대여중, 수리중 등)의 흐름이 실제 현장 라이프사이클과 완벽히 일치해야 한다.
2. **발생되는 사건(Event) 기록의 무누락 DB 저장**: 출고, 검수, 배차, 반납, 정비, 상태 변경 등 모든 비즈니스 이벤트는 이력 테이블 및 DB 로그에 빠짐없이 기록되어 추적 가능해야 한다.
3. **임직원 업무의 최소 조작 & 최상의 편의성**: 불필요한 번복 입력이나 이중 조작을 없애고, 최소한의 클릭 및 단축 흐름으로 직관 처리되도록 구상한다.

### 1.3 출고 검수 승인 마감 시 자산 상태 `RENTED` (`대여중`) 전환 원칙
- 출고 검수 승인이 최종 완료되는 즉시 자산 상태는 **`RENTED` (`대여중`)**으로 전환된다.
- **배차 단계에서 자산 상태를 조작하지 않는 이유**: 배차 취소 시 자산 상태 롤백 여부를 판단할 수 없고, 배차 담당자는 실질적인 자산의 유동이나 계약 취소 여부를 권한/인식 상 직접 처리할 수 없다. 따라서 배차 단계에서 상태를 조작해서는 안 되며, 자산의 대여 상태 전환은 출고 검수 승인 시점에 완결된다.

## 👔 [카테고리 II] 부서 간 권한 및 업무 책임 (Domain R&R Policy)

### 2.1 영업 부서와 출고/자산 부서 간 R&R 엄격 분리
- **영업 부서의 역할 & 권한**: 고객사과의 계약 관점에서 '사용 권리 보장' 책임을 이행하기 위해, 회사에 **동일/동등 모델 장비의 대차 교체 요구(의뢰)**를 전송하는 것까지 담당한다. 영업사원이 개별 출고 자산번호를 직접 선택/지정하는 행위는 부서 R&R을 위반하므로 금지한다.
- **출고/자산 부서의 역할 & 권한**: 영업사원의 대차 요구를 받아, 본인 부서의 권한과 책임 하에 **자사 자산(임대가능)을 초이스하거나 자산 부족 시 외부 타사 임차(전대) 장비를 매핑하여 출고를 지원**한다.

### 2.2 대차/교체 시 계약 속성 100% 자동 상속 원칙 (Contract Property Inheritance)
- 대차 교체가 발생하여 새로 현장에 들어가는 대차 장비(자사 자산 또는 외부 임차 장비)는 최초 계약이 자산에 요구하는 **렌탈료 단가 조건, 청구/명세서 마감일 조건, 현장/작업지시 속성, 영업담당자 속성**을 100% 자동으로 상속(Inherit)받아야 한다.

### 2.3 대차/교체 배차 의뢰 단일 'EXCHANGE' 1건 발행 원칙 (Single Exchange Delivery Order Standard)
- "모든 업무는 의뢰에 의해 발생한다"는 원칙과 왕복 운송비 할인 적용 배경에 따라, 대차/교체 발생 시 출고/입고 2건으로 파편화하여 배차를 발행하지 않는다.
- 배차 속성에 **`'EXCHANGE'` (`교환`)**를 정식 적용하여, **단일 대차 요구에 대해 `'EXCHANGE'` 1건의 왕복 배차 의뢰만 발생**시킨다.
- 배차 대장에서 1건의 교환 배차로 왕복 운송비 정산 및 출고/회수 1:1 업무 체인을 통합 관리하며, 시차 출고 등 특수 예외 상황은 담당자의 수동 분할 입력을 통해 대처한다.

## 🎨 [카테고리 III] UI/UX 표기 및 레이아웃 표준 (UI/UX Standards)

### 3.1 건조하고 직관적인 전문 용어 UI 표기 정책 (Professional UI Label Standard)
- 시스템 화면의 모든 타이틀, 버튼, 카드 라벨, 가이드 문구에는 과장되거나 현란한 수식어(예: "컨트롤 타워", "360도 통합", "1초 검색", "불시 발행" 등)를 일절 금지한다.
- 사용자는 숙련된 렌탈 실무 전문가이므로 **건조하고 명확하며 직관적인 명칭만을 단일 표준으로 사용**한다. (예: `계약 상세`, `계약 기본 정보`, `체결 자산 목록`, `계약 변경 이력`, `기간 연장/단축`, `계약 승계`)

### 3.2 셀 및 레이블 줄바꿈 방지 원칙 (No-Wrap & Flex-Shrink-0 Standard)
- 전문 관리 화면의 데이터 테이블 및 폼 필드/필터 패널 레이블 텍스트가 위아래로 줄바뀜(Word-wrap)되어 UI가 찌그러지는 현상을 엄격히 금지한다.
- 모든 레이블 및 테이블 셀에는 `white-space: nowrap`과 필요 시 `flex-shrink: 0`을 적용하여, 어떤 화면 해상도에서도 텍스트가 가로 1줄로 정교하고 시원하게 렌더링되어야 한다. 횡 스크롤 발생 시 `[상세 ➔]` 버튼 등 핵심 액션 컬럼은 테이블 가장 왼쪽(첫 번째 컬럼)에 배치한다.

### 3.3 사용자 맞춤형 직무 중심 ToDo 피드 대시보드 정책
- 대시보드는 불필요한 공통 위젯을 배제하고, 로그인한 사용자의 직무 및 역할에 특화된 실시간 당면 과제만 카드뉴스(ToDo 피드) 형태로 직관적으로 노출한다.

### 3.4 레이블-입력 필드 상하 스택 배치 원칙 (Vertical Header-Label Layout Standard)
- 레이블(Label)과 입력 필드(텍스트박스, 드롭다운, 셀렉트박스, 날짜 입력창 등)로 구성되는 모든 UI 폼 및 필터 패널은 레이블을 좌측 가로 배치(`[레이블:] [입력창]`)하지 않는다.
- **레이블이 헤더처럼 입력창 바로 위에 위치하는 상하 세로 스택 구조(`flex-direction: column`, `gap: 4px`)**를 전사 단일 표준 UI 디자인 컨셉으로 예외 없이 이행한다.

### 3.5 좌상단 ➔ 우하단 시선 및 업무 동선 일치 원칙 (Gutenberg Z-Pattern Standard)
- 모든 전문 관리 및 대사 화면의 UI 레이아웃은 사용자의 시선 흐름(Eye-tracking)과 실제 업무 완결 순서가 **좌측 상단(Start)에서 우측 하단(Terminal Action)으로 자연스럽게 대각선/Z자로 흐르는 4단계 동선 구조**를 엄격히 준수한다:
  1. **좌측 상단 (Start / Scope)**: 조회 조건(정산 연월, 거래처, 지급 미완료 대상 스코핑) 배치.
  2. **우측 상단 (Input / Pipeline)**: 데이터 유입(엑셀 업로드, 양식 다운로드, 검색 실행) 버튼군 배치.
  3. **중앙 본문 (Body / Inspection)**: 화면 세로 영역의 80~85%를 차지하는 고밀도 1:1 대사 그리드/테이블 배치 (인라인 확인 및 즉시 차액 승인).
  4. **우측 하단 (Terminal Action)**: 대차대조 합계 검증 요약과 함께 최종 완결 버튼(`[통합 지급요청]`, `[최종 결재]`)을 고정 배치.
- **목적 지향 Z-패턴 설계를 위한 4대 본질 질문 (Teleological 4-Questions Framework)**:
  모든 화면 설계 시 엔지니어와 기획자는 아래 4대 질문에 대한 명확한 개념 흐름을 UI에 투영해야 한다:
  1. **질문 1: "이 메뉴의 최종 목표(Terminal Objective)는 무엇인가?"** ➔ **④ 우하단 (Terminal Action)**의 최종 완결 버튼(`[통합 지급요청]`, `[최종 결재]`) 정의.
  2. **질문 2: "그 목표에 도달하기 위해서 알아야(세팅해야) 하는 정보는 무엇인가?"** ➔ **① 좌상단 (Scope)** & **② 우상단 (Pipeline)**의 범위/유입 데이터 정의.
  3. **질문 3: "어떤 순서(Cognitive Sequence)로 인지와 조작이 흘러가고 있는가?"** ➔ **③ 중앙 본문 (Inspection)**에서 상태 조망 ➔ 차액/원인 분석 ➔ 인라인 원클릭 조치의 1-Way 동선 정의.
  4. **질문 4: "최종점에 도달하면 어떤 결과(Audit Result)를 알게(확정하게) 되는가?"** ➔ **④ 최하단 대차대조 검증식**(`📄 청구총액 = 🟢 확정액 + 🚫 반려액 | ⚖️ 대차 차액 ₩0`)을 통한 무결성 확정.
- **금지 패턴**: 화면 중앙에 최종 액션 버튼을 띄우거나 좌하단에 완결 버튼을 두어 시선이 역류(Reverse-Flow)하는 배치를 절대 금지한다.

### 3.6 업무 본질 속성별 2대 UI 아키타입 표준 (Card Dossier vs High-Density Grid)
화면 및 메뉴를 설계할 때는 업무의 본질 속성(Task Nature)에 따라 아래 2대 UI 아키타입 중 하나를 명확히 선택하여 이원화 적용한다:
1. **📋 유형 A: [요청 처리형 업무 (Request Execution)] ➔ 카드형 / 마스터-디테일 스튜디오 (Card / Dossier)**
   - **본질**: "발행된 요청 1건을 접수하여 면밀히 검토하고 판단·조치·완결하는 업무"
   - **UI 특성**: 개별 1건의 상세 컨텍스트(자연어 요청 원문, 제원, 지도/날씨, 복수 기사 배정, 특이 메모 등)를 화면에 최대한 넓고 깊게 노출. 팝업을 열지 않고도 1화면에서 360도 판단이 가능하도록 구성.
   - **대표 메뉴**: 배차/운송 기사 배정(`TruckDispatch` 탭 1), 출고 검수 승인(`OutboundInspection`), 입고 정비/수리 조치(`Repairs`).
2. **📊 유형 B: [기간 조회 및 정산/정리형 업무 (Period Audit & Reconciliation)] ➔ 고밀도 그리드형 (High-Density Multi-Column Grid)**
   - **본질**: "지정된 기간 동안 완료된 수십~수백 건의 데이터를 비교, 검증, 차액 분석, 일괄 확정/마감하는 업무"
   - **UI 특성**: 행 높이 38~42px 슬림 테이블로 화면 세로 영역의 80~85%를 작업대로 확보. 한눈에 15~30건을 동시 조망하며 인라인 차액 분석, 원클릭 승인/제외 조치, 우하단 대차대조 합계 검증(`청구 = 확정 + 반려 | 차액 ₩0`)으로 종결.
   - **대표 메뉴**: 월말 운송료 대사(`TruckDispatch` 탭 2), 월말 매출 청구 대장(`Billings`), 통장 입금 1:1 대사(`BankMatching`), 외상매출금 정산 대장(`Receivables`).
- **단일 메뉴 내 탭별 이원화**: `TruckDispatch`처럼 동일 메뉴 내에서도 탭 1(발행요청 처리 ➔ 카드형)과 탭 2(월말정산 정리 ➔ 그리드형)처럼 탭별 목적에 맞춰 서로 다른 아키타입을 독립 적용할 수 있다.

## 💰 [카테고리 IV] 회계 정산 및 이력 추적성 (Accounting & Audit Trail)

### 4.1 자산별 매출 기여액 정밀 일할 집계 정책 (Asset Revenue Contribution Pro-Rata Policy)
- 시스템은 복잡한 원가 차감 손익 집계를 수행하지 않으며, **각 자산별 누적 매출 기여액(Revenue Contribution)만을 1원도 틀림없이 정밀 일할 집계**한다.
- 대차 교체 발생 시:
  - 회수 자산(전자산): 교체 전일까지의 가동 일수 × 일할 단가로 매출 기여액을 최종 확정 마감.
  - 대차 자산(후장비): 교체 당일부터의 가동 일수 × 일할 단가로 바통을 승계받아 매출 기여액을 누적 집계.
- 전체 계약 매출 총액과 개별 자산별 누적 매출 기여액의 합은 100% 일치해야 한다.

### 4.2 대차 교체 이력 전자산 ➔ 후장비 1:1 완벽 추적성(Audit Trail) 보장
- 대차 교체 발생 시 `contractHistory` 및 타임라인에 `changeType: 'EXCHANGE'` 이력을 명시하여, **어느 전자산(회수 대상)이 어떤 후장비(대차 자산)로 교체되었는지 1:1 논리적 연결 관계**를 무누락 보존한다.

## 🔍 [카테고리 V] 개발 검증 및 리포트 방법론 (Development Verification Protocol)

### 5.1 리포트/통계 개발 시 2단계 검증 정책 (Report Math & Schema Audit Policy)
- 신규 리포트, 통계, 수익성 기능을 개발하거나 수용할 때는 근거 없는 단정이나 섣부른 대답을 일절 금지한다.
- **2단계 검증 방법론 필수 이행**:
  1. **수학적/논리적 수식 정립**: 리포트 집계에 필요한 모든 변수와 계산식을 수학적 수식 기호로 명확히 정립한다.
  2. **DB 스키마 1대1 검증**: 수식에 사용되는 모든 변수들이 현재 DB 스키마(`db.ts` 등)의 컬럼 및 이벤트 데이터로 1:1 저장되고 있는지 검증한다.
- 검증 결과 부족하거나 누락된 데이터 필드가 발견되면, 개발 착수 전에 사장님께 스키마 보완점과 대안을 먼저 정밀 보고하고 승인을 받은 뒤 개발을 집행한다.

### 5.2 전 스토리지/DB 저장 성공 검증 및 무음 실패 방지 정책 (Zero Silent Failures)
- 모든 데이터 CUD(생성/수정/삭제) 액션은 `await db.awaitPendingWrites()`를 동기로 대기 수행하여 성공 여부를 검증한다. 저장 실패 시 절대로 무음 처리(Silent Swallow)하거나 성공 메세지를 먼저 띄우지 말고 `showErrorModal(errMessage)`을 즉시 표출한다.

### 5.3 단일 진실의 원천(SSOT) 및 로컬 DB 스키마 정합성 자가 검증
- 전사 메타데이터(메뉴, 권한, 스키마 라벨)는 전사 단 하나의 원본 파일(SSOT)에만 정의한다.
- 로컬 스키마 정의(`schema.sql` 등)를 파싱하여 원격 DB와의 정합성을 자동 검증하고, RLS 정책 오류 시 `anon` 및 `authenticated` 롤에 대한 SELECT/INSERT/UPDATE 허용 Policy를 멱등성(DROP IF EXISTS 선행) 있게 DDL로 동적 자동 생성한다.

### 5.4 반복 개편 3회 원칙론적 자동 검토 트리거 정책 (Repeat-Refactor Review Policy)
- **동일 프로세스(화면/기능/로직)에 대해 3번째 개편 요구가 발생하는 경우**, 사장님의 별도 지시가 없더라도 해당 프로세스에 대한 **원칙론적 검토를 자동으로 선행 집행**한다.
- **검토 항목**: ①현재 구조가 전사 표준 헌장(카테고리 I~VI)에 정합하는가, ②동일 개편이 반복되는 근본 원인(설계 결함, R&R 불명확, 데이터 구조 미비 등)이 무엇인가, ③즉시 구현 vs. 근본 재설계 중 어느 접근이 장기적으로 더 높은 편익을 산출하는가.
- 검토 결과 **근본적인 설계 재검토가 필요하다고 판단**되면, 단순 지시 이행 전에 사장님께 **판단 의견(판단 요지 + 권고안)**을 먼저 보고하고 지시를 기다린다.
- 단순 반복이 아닌 **점진적 요구 확장**으로 판단되는 경우에는 통상 개편을 집행하되, 검토 결과를 간략히 첨부하여 보고한다.

### 5.5 도메인 관통 스트레스 테스트(WTT) 정의 및 스트레스 주입 원칙 (Domain Penetration Stress Test Standard)
- **본질 정의**: WTT(Work-Through Test)는 단순한 단위/통합 테스트나 기능 검증이 아니며, **"교과서적 정상 프로세스(Happy Path)에 실제 현장의 물리적 마찰과 인간의 이해관계를 강력한 스트레스로 주입하여, 시스템이 이를 온전히 해결하고 보존 법칙을 지켜낼 능력이 있는지를 끝까지 추적·검증하는 도메인 관통 스트레스 테스트(Domain Penetration Stress Test)"**로 전사 표준 정의한다.
- **4대 운영 철학**:
  1. **물리적 현장의 마찰 계수 주입**: 화면 상태값만 바꾸는 가짜 흐름을 배제하고, 실제 장비의 안전옵션 볼팅, 오염 세척, 현장수리 불가 등 현장 물리적 제약을 시나리오에 반드시 투하한다.
  2. **경로의 비대칭성 및 부분 분기**: 들어갈 땐 경유 ➔ 나갈 땐 직반납 등 비대칭 경로와 동일 계약 다수 장비 중 1대만 튀는 부분 예외 분기를 테스트한다.
  3. **비용(돈)과 책임(R&R)의 귀속선 추궁**: 돌발 발생 시 운송비 부담 주체(`paidBy: CUSTOMER/OURS/VENDOR`), 전자산 전일 마감 ➔ 후장비 당일 승계, 유상 AS 채권 분리 등 사법적·회계적 귀속선을 명확히 긋는다.
  4. **종단 보존 법칙(Conservation Law)의 무결성 확정**: 날짜 보존(가동일 합계 = 역일), 수지 보존(`총매출 = 총지출 + 순마진 | 대차 차액 ₩0`), 상태 보존(정비점수 가산 ➔ 0점 복원)의 3대 보존 법칙이 1원/1일/1로그의 오차도 없이 입증되어야 완료 승인한다.
- **돌발·스트레스 주입 5대 생성 축 (5-Axis Stress Injection Matrix)**:
  모든 비즈니스 프로세스 검증 시 아래 5대 축을 교차 결합하여 10~20회의 시나리오를 필수 도출한다:
  ① **공간 축**: 직송 vs 당사 경유 vs 제3 주기장 임시 보관
  ② **물리 축**: 옵션 장착/탈거, 모터 소손, 유압 누유, 도색 오염, 배터리 방전
  ③ **시간 축**: 월초 1~5일(조기), 월중 15일(표준), 월말 임박 28~29일, 10일 단기, 시차 출고
  ④ **비용 축**: 고객 전액 청구, 당사 순손실 부담, 원사 정산 공제, 일할 단가 특약, 선수금 차감
  ⑤ **수량 축**: 단일 1대, 다수 장비 계약 중 1대만 부분 교체/부분 반납, 연속 2회 복합 대차

## 📦 [카테고리 VI] 버전 관리 및 배포 정책 (Version Control & Deployment)

### 6.1 사용자 정의 4단계 버전 넘버링 및 릴리즈 노트 시간 기록 규칙
- 버전 형식: `vX.Y.Z.Build.N` (X: 메이저, Y: 신규 메뉴/DB 테이블 추가, Z: 기존 메뉴 기능 확장/리팩토링, Build.N: 버그패치/UI 미세조정).
- 모든 Git 커밋 및 `RELEASE_NOTES.md` 작성 시 위 4단계 버전과 구체적인 배포 날짜/시간(예: `2026-07-29 21:30`)을 예외 없이 상시 표기한다.

### 6.2 커밋/푸시 정책 및 단축어 "ㄹㅇ" 일괄 실행 규칙
- **로컬 커밋**: 사용자의 명시적 지시("커밋해줘")가 있을 때만 `git commit` 수행.
- **원격 푸시**: 사용자의 명시적 지시("푸시해줘", "ㄹㅇ")가 있을 때만 `git push` 수행.
- **요구사항 임시 기록**: 모든 개발 요구사항은 프로젝트 루트의 `dev_temp.md`에 기록한 뒤 사장님의 명시적 개편 지시 지점에서 구현.
- **단축어 "ㄹㅇ"**: `dev_temp.md` 미반영 요구사항 코드 구현 ➔ `RELEASE_NOTES.md` 작성 ➔ `git add -A && git commit && git push origin main` 논스톱 일괄 집행 (Vercel 배포 제외).

### 6.3 Vercel 최근 최대 12개 배포 슬롯 자동 유지 정책 (Auto-Purge Policy)
- Vercel 프로덕션 배포는 `main` 브랜치 push 시에만 트리거한다.
- **Error(실패) 상태 배포 슬롯 관리**: Vercel 빌드/배포 중 `Error` 상태가 발생한 배포 슬롯은 **슬롯 개수 카운터에 포함시키지 않고 발견 즉시 100% 무조건 자동 삭제(Purge)**한다.
- **Ready(정상) 배포 슬롯 관리**: 정상 동작 중인 배포 슬롯은 항상 **최근 최대 12개 이하**만 상시 청정하게 유효 보존하며, 12개 초과 시 Vercel API/CLI를 호출하여 **가장 오래된 과거 정상 배포 슬롯들을 자동으로 삭제(Purge)**한다.
